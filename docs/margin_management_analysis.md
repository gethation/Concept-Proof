# 雙帳戶保證金管理系統 — 分析與實作交接文件

> 交接對象:負責實作保證金監控/轉帳決策系統的 agent
> 分析日期:2026-07-05(樣本 2026-03-12 ~ 2026-06-29)
> 分析與模擬程式:[scripts/simulate_margin_transfers.py](../scripts/simulate_margin_transfers.py)
> 模擬結果快照:[data/processed/margin_transfer_simulation.json](../data/processed/margin_transfer_simulation.json)

## 1. 問題定義

TSM/QFF 配對策略在兩個獨立帳戶執行:

| 帳戶 | 交易標的 | 計價 | 每邊名目 |
|---|---|---|---|
| Binance | TSMUSDT.P 永續合約 | USDT | 100 萬 TWD 等值 |
| 富邦期貨 | TAIFEX 小型台積電期貨 (QFF) | TWD | 100 萬 TWD(約 4-5 口) |

配對整體市場中性,但**每個帳戶各自承受完整的單腿方向風險**:TSM 漲 5%,
空 perp 的帳戶就虧 5 萬/每百萬名目,期貨帳戶賺 5 萬(或反向)。虧損側的
保證金會耗盡,必須從賺錢側轉帳補足。

**轉帳限制**(使用者given):
- 每天最多一次
- 只能在台北時間 **10:00** 發起
- 當天 **17:00** 入帳

因此「無援助窗口」只有兩種:
- **7 小時**:今天 10:00 發起 → 17:00 入帳前要自撐
- **31 小時**:今天 10:00 決定不轉 → 下一次機會是明天 10:00 發起、17:00 入帳

**週末不存在額外窗口**:策略在週五最後一個交易時段強制清倉
(`friday_session_end_force_close`),已用數據驗證——樣本內 260 個週六 bar、
16 個週五收盤**全部空倉**。週五 10:00 不轉的實際窗口只到週六 05:00(約 19h),
被 31h 的數字覆蓋。

## 2. 已確立的量化結論

### 2.1 單腿最大逆向波動(每 100 萬 TWD 名目,74 個 10:00 決策點實測)

| 窗口 | p50 | p90 | p99 | 最大 |
|---|---|---|---|---|
| TSM 腿 7h | 0.65% | 1.50% | 1.93% | 2.09% |
| TSM 腿 31h | 2.77% | 5.19% | 6.75% | **7.20%** |
| QFF 腿 7h | 1.03% | 1.56% | 2.47% | 2.96% |
| QFF 腿 31h | 2.41% | 4.14% | 7.39% | **8.37%** |

(量測方式:從每個決策點起算、窗口內對起點的最大雙向偏移,取絕對值較大者
——路徑相依,不是端點差。重跑:`conda run -n Quant python scripts/simulate_margin_transfers.py`)

### 2.2 政策模擬結果(用回測實際持倉逐 bar 重放,含各腿手續費)

觸發門檻固定為 Binance 11% / 富邦 20%(見第 3 節),掃資金目標水位:

| 目標水位(佔名目) | 3.6 個月轉帳次數 | 觸及最低比率 (B/F) | 維持保證金穿越 |
|---|---|---|---|
| 25% | 2 | 10.3% / 15.7% | 0 |
| **30%(建議)** | **0** | **24.5% / 20.3%** | **0** |
| 35% | 0 | 29.5% / 25.3% | 0 |

30% 是拐點:配對兩邊的腿損益跨交易互相回收,300k 緩衝下餘額幾乎不漂移。
注意:樣本內 0 次轉帳有運氣成分,實際預期約 0-1 次/月。

## 3. 政策規格(直接實作這個)

比率定義:`帳戶權益 / 該腿名目(100 萬 TWD)`。Binance 側用 USDT 計都可以
(比率無關幣別)。

| 層級 | Binance | 富邦 | 動作 |
|---|---|---|---|
| **紅線**(任何時刻) | < 5% | < 13.5% | **立即平倉/減倉**——轉帳已來不及(公式:維持保證金率 + 7h 最大波動) |
| **強制轉帳**(每天 10:00 檢查) | < 11% | < 20% | 今天就發起轉帳,金額 = (30% − 現值) × 名目,從另一帳戶撥(公式:維持保證金率 + 31h 最大波動) |
| **目標水位**(進場配置/轉帳後) | 30% | 30% | 每 1M/1M 配對共鎖 60 萬 TWD |
| **空倉再平衡** | 偏離 30% | 偏離 30% | 空倉時擇機回補到 30/30(零風險窗口,不急) |

換算參考(usdttwd ≈ 31.8):30% ≈ 300k TWD ≈ 9,400 USDT(Binance ≈ 3.3 倍
槓桿;富邦 ≈ 1.8 倍原始保證金)。Binance 建議用**逐倉(isolated)**,行為與
模擬一致。

## 4. 待實作系統的需求

建議 MVP 為**半自動**:系統做監控、計算、通知;轉帳與平倉由人執行。
不要在 MVP 自動下單或自動發起轉帳。

1. **每日 10:00 檢查 job**(週一~週五):
   - 讀兩帳戶權益(Binance Futures API `balance`;富邦權益數——API 或人工輸入 fallback)
   - 算比率、對照門檻,產出決策:「今天要不要轉、轉多少、哪個方向」
   - 通知使用者(方式待定:LINE/Telegram/email),含金額與截止提醒
2. **盤中紅線監控**(建議每 15 分鐘,持倉時段):
   - 任一帳戶低於紅線 → 緊急告警(明確寫「平倉,不要等轉帳」)
3. **入帳確認**(17:00 後):驗證轉帳到帳、比率回到目標,失敗則告警
4. **記錄**:每次檢查/決策/轉帳寫入 log(csv 或 sqlite),供日後校準
5. **參數外置**:門檻、目標、維持保證金率放設定檔,不要寫死——維持保證金率
   會隨交易所/期交所公告變動

## 5. 實作前必須人工核實的參數(目前是佔位值!)

| 參數 | 佔位值 | 核實來源 |
|---|---|---|
| Binance TSMUSDT.P 維持保證金率 | 2.5% | Binance 保證金階梯表(股票類 perp 可能更高,且隨倉位大小分層) |
| TAIFEX 小台積電原始/維持保證金 | 13.5% / 10.35% | 期交所公告(隨風險價格係數級距調整) |
| 富邦盤中強制平倉條件 | 權益 < 維持保證金 | 富邦契約(常見為風險指標低於約定比率) |
| 轉帳實際路徑與時程 | 10:00 發起/17:00 入帳 | 使用者實測(含 USDT↔TWD 轉換環節) |

核實後套公式重算門檻:**強制轉帳 = 維持保證金率 + 8%;紅線 = 維持保證金率 + 3%**
(8%/3% 分別是 31h/7h 樣本最大波動進位)。改參數後重跑
`scripts/simulate_margin_transfers.py --binance-maint X --fubon-maint Y ...` 驗證。

## 6. 邊界情況與已知風險

- **樣本限制**:74 個決策點(3.6 個月),含 4 月台積電財報波動,但蓋不住更極端
  的跳空(如 ADR 財報夜 ±10%+)。從 30% 起跳可撐一次極端日;連續兩天極端波動
  會考驗紅線——這是單日轉帳限制的殘餘風險,系統要把紅線告警做可靠
- **名目縮放**:所有 % 門檻對名目線性縮放;若每邊名目改變,金額跟著乘
- **策略改組合**(gated w33 + w133 各半):兩本書 75% 同方向,合併帳戶的單腿
  風險近似相加,本政策照名目總額套用即可
- **假日**:台灣銀行假日不能轉帳的日子,前一個營業日的檢查要用更長窗口
  (實作時把「下一個可轉帳日」做成日曆查詢,不要寫死 +1 天)
- **總資金漂移**:策略獲利會讓總權益成長,定期(如每月)在空倉時把超額提到
  外部準備金

## 7. 驗收標準

1. `scripts/simulate_margin_transfers.py` self-test 通過(已含:不需轉帳/恰好
   一次轉帳/穿越維持保證金三個情境)
2. 監控系統在歷史重放下與模擬器決策一致(同樣的 74 個決策點、同樣的轉帳建議)
3. 紅線告警在模擬的 13% 資金情境下會觸發
4. 所有門檻參數改動只需改設定檔
